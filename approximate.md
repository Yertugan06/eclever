# Proposed Architecture & Scope

Bachelor's Thesis · Preliminary Technical Design · v1.0

Project: Development of an AI-Based Adaptive and Personalized Learning Platform for Teaching Programming to Students in Grades 6–8

Я предлагаю архитектуру для дипломной работы, в которой есть полноценная образовательная платформа, адаптивный движок и AI-репетитор. При этом сложность должна оставаться реалистичной для студенческой команды.

Основная идея: система не просто проверяет код и объясняет ошибки, а оценивает освоение конкретных навыков, подбирает следующие задания и регулирует уровень помощи.

## 1. Scope дипломного проекта

MVP / Core Scope

Что обязательно реализовать

- Регистрация и роли Student / Teacher.
- Структурированный курс Python для 6–8 классов.
- Интерактивный редактор кода с автоматической проверкой.
- Skill Graph — зависимости между изучаемыми навыками.
- Student Knowledge Model — отслеживание освоения навыков.
- Adaptive Learning Engine — рекомендации по сложности и следующим заданиям.
- AI Tutor — объяснения ошибок и многоуровневые подсказки.
- Student Dashboard и Teacher Dashboard.
- Сбор событий и метрик для анализа качества адаптации.

Research / Extended Scope

- BKT для вероятностной оценки знаний.
- Сравнение BKT с rule-based baseline.
- Определение учебных затруднений по попыткам и взаимодействиям.
- Повторение материала для проверки сохранения знаний.
- Эксперименты по качеству рекомендаций и AI-подсказок.

Out of Scope для первой версии

- DKT без достаточного датасета.
- CV-анализ лица и автоматическое распознавание эмоций.
- Голосовой AI, STT/TTS.
- Полностью автономная генерация учебной программы через LLM.
- Поддержка нескольких языков программирования.
- Микросервисная архитектура с Kubernetes.

Ограничение контента: для MVP — Python, примерно 12–20 навыков, 40–80 заранее подготовленных упражнений с тестами и 3 уровнями сложности. Это проектные ориентиры, а не обязательные требования диплома.

## 2. High-Level System Architecture

Логическая архитектура. Все внутренние модули FastAPI могут работать в одном приложении. Code Runner изолируется отдельно; LLM вызывается через внешний API.

Архитектурный стиль: Modular Monolith + Isolated Code Execution Worker. На данном масштабе это проще, чем полноценные микросервисы.

## 3. Основные backend-модули

| Модуль                   | Ответственность                                 |
| ------------------------ | ----------------------------------------------- |
| Auth & User Management   | Учетные записи, роли, классы и доступы          |
| Curriculum Engine        | Темы, навыки, зависимости и учебные материалы   |
| Exercise Engine          | Задания, тест-кейсы, уровни сложности           |
| Submission & Assessment  | Отправка кода, запуск тестов, результаты        |
| Student Knowledge Model  | Состояние освоения каждого навыка               |
| Adaptive Learning Engine | Выбор следующих упражнений и повторений         |
| AI Tutor Service         | Контекстные подсказки и объяснения ошибок       |
| Learning Analytics       | История попыток, прогресс, отчёты преподавателя |

Для каждой задачи должны быть явно указаны связанные навыки, сложность и критерии проверки. Одна задача может проверять несколько навыков, но для первой версии удобнее иметь один основной навык и дополнительные зависимости.

## 4. Pedagogical Model & Adaptive Learning

Это центральная часть проекта. Я бы разделил её на три самостоятельных компонента.

Knowledge Estimator

Определяет, насколько ученик владеет каждым навыком. Начальная реализация — rule-based, экспериментальная — BKT.

Mastery Decision Policy

Определяет, достаточно ли доказательств освоения навыка: самостоятельные решения, перенос знаний, отложенные проверки.

Adaptive Recommendation Engine

Выбирает следующую задачу, изменение сложности, повторение темы или дополнительную помощь.

### Пример модели состояния ученика

```
{
  "student_id": "student_123",
  "skill_id": "python_for_loops",
  "mastery_probability": 0.78,
  "mastery_status": "practicing",
  "independent_successes": 2,
  "hint_usage": 1,
  "transfer_assessment_passed": false,
  "retention_assessment_passed": false
}
```

При этом `mastery_probability` — оценка модели BKT, а `mastery_status` — результат педагогических правил. Это разные сущности, и не нужно их смешивать.

Предлагаемые состояния:

`NOT_STARTED → LEARNING → PRACTICING → MASTERED → REVIEW_DUE`

Переходы должны основываться на конкретных доказательствах, а не просто на количестве решённых задач. Пороговые значения можно сначала задать как гипотезы и затем проверить.

## 5. AI Tutor — Scope

AI Tutor не должен самостоятельно определять окончательную оценку знаний. Его задача — помогать ученику понимать материал.

Предлагаю четыре уровня подсказок:

| Уровень | Тип помощи               | Пример                                                      |
| ------- | ------------------------ | ----------------------------------------------------------- |
| L1      | Направляющий вопрос      | «Что происходит со значением переменной в каждой итерации?» |
| L2      | Концептуальная подсказка | «Проверь, сколько раз выполняется тело цикла»               |
| L3      | Локальная диагностика    | «Обрати внимание на границы `range()`»                      |
| L4      | Пошаговое объяснение     | «Разберём аналогичный пример вместе»                        |

Главная идея — помощь постепенно усиливается, но решение текущего задания не выдаётся сразу.

Технически:

- LLM получает описание задачи, код ученика, результаты проверки и разрешённый уровень подсказки.
- Backend проверяет соответствие ответа ожидаемому формату и педагогическим ограничениям.
- История подсказок сохраняется, чтобы учитывать степень самостоятельности.
- Ответы AI ограничены учебным контекстом, с защитой от нежелательного контента для школьников.

Для диплома достаточно одного LLM-провайдера с абстрактным интерфейсом, без сложной многоагентной архитектуры.

## 8. Evaluation Scope для диплома

Я предлагаю три уровня оценки.

| Направление            | Метрики                                                    |
| ---------------------- | ---------------------------------------------------------- |
| Knowledge Tracing      | AUC, log loss, Brier score, calibration                    |
| AI Tutor               | Hint correctness, solution leakage, pedagogical compliance |
| Learning Effectiveness | Pre-test/post-test, самостоятельность, retention, transfer |

В эксперименте по knowledge tracing важно разделять данные по ученикам и учитывать временной порядок, чтобы не получить утечку данных.

Для оценки эффективности обучения лучше сравнить адаптивную и фиксированную траектории на одинаковых учебных целях. Если школьников привлечь не получится, ограничиться техническими экспериментами и не делать выводов о доказанном улучшении обучения.

## 9. Phased Development Scope

Phase 1 — Educational Platform

Auth, curriculum, skill graph, code editor, sandbox, упражнения и сохранение попыток.

Phase 2 — Adaptive Learning

Rule-based baseline, mastery tracking, рекомендации, BKT-эксперимент.

Phase 3 — AI Tutor

Контекстные подсказки, педагогические ограничения, история помощи и оценка качества.

Phase 4 — Analytics & Evaluation

Дашборды, сбор исследовательских данных, сравнение моделей и подготовка результатов защиты.

## Итоговый рекомендуемый scope

Для диплома я бы зафиксировал пять основных результатов: работающая учебная платформа, структурированная педагогическая модель, адаптивный движок с BKT и rule-based baseline, AI Tutor и экспериментальная оценка.

CV, голосовой интерфейс и анимированный маскот можно оставить в проектном замысле, но они не должны определять успех основной системы.

Самый сложный и важный вопрос, который необходимо решить на этапе проектирования, — как перевести поведение школьника в достоверную оценку знаний и затем в педагогически правильное действие. Именно здесь находится содержательное ядро вашей дипломной работы.
